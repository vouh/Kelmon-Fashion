# Known Issues and Accepted Risks

Open items as of 2026-09-27. Listed so they are decisions rather than
oversights. None is a reason not to launch; several should be closed before
handling significant volume.

Severity is about impact on Kelmon, not CVSS.

---

## High

### 1. M-Pesa callbacks are unauthenticated

`/api/mpesa/callback` accepts any POST. Safaricom does not sign callbacks, and
the handler cannot distinguish a genuine result from a forged one.

**Impact.** Anyone who learns a `CheckoutRequestID` can mark that order paid
without paying, and trigger a loyalty-points award.

**Why it is not trivial to exploit.** The id is generated by Safaricom, never
returned to the storefront UI, and unguessable. Only the initiating client sees
its own.

**Mitigation available now:** restrict the route to Safaricom's published egress
IP ranges at the edge (Vercel firewall or a middleware allow-list), and reconcile
against the Daraja transaction-status API before treating an order as paid.

**Accepted for now** because the id is unguessable and order values are small.
Revisit before scaling.

### 2. A price change mid-session charges the new price silently

`/api/orders` re-prices every line from the catalogue and ignores the client's
figures — correct for preventing tampering
([ADR-0004](../architecture/decisions/0004-server-side-repricing.md)), but it
means a customer who loaded the page before a price rise is charged the higher
amount with no warning.

**Correct behaviour:** detect the difference, show the customer the new total,
and require confirmation before the STK Push.

**Fix:** have the client send the total it displayed, compare server-side, and
return `409` with both figures so the UI can re-confirm. The submitted figure is
still never used for the charge — only for detecting drift.

## Medium

### 3. No rate limiting anywhere

No endpoint is throttled. Notably:

- `/api/mpesa/stk-push` — repeated calls spam a customer's handset with PIN
  prompts, and burn Daraja quota.
- `/api/orders` — unbounded order creation per account.
- Server Actions — an admin can loop writes.

Supabase Auth rate-limits sign-in attempts, so credential stuffing is partly
covered. Nothing else is.

**Fix:** per-user and per-IP limits at the edge. The STK route matters most, both
for cost and because it is user-visible harassment.

### 4. No audit log of admin actions

Admins can delete orders, reviews and products with no record of who did what.
With more than one admin there is no way to reconstruct a mistake or attribute a
deletion.

**Fix:** an `audit_log` table written by each Server Action (actor, action,
target, timestamp, before/after), insert-only, admin-readable.

Related: `deleteOrder` and `deleteProduct` are hard deletes. Prefer
`setProductActive(id, false)`; consider soft-deleting orders.

### 5. Stock is never decremented

`products.stock` is displayed and editable but no order reduces it. Inventory
shown to customers drifts from reality, and overselling is possible.

**Fix:** decrement inside a transaction when the order is created, with a
`check (stock >= 0)` guard to reject overselling rather than going negative.
Decide whether to reserve at order time or at payment time — reserving at
payment risks selling an item twice while a PIN prompt is pending.

### 6. Salon bookings are not wired up

`salon_bookings`, its RLS policies and `lib/supabase/salon.ts` all exist, but
`/salon` is still the original waitlist UI — no booking can be created, and the
admin panel has no bookings screen.

Not a defect, just unfinished: it needs decisions about availability and
scheduling. The schema is ready.

## Low

### 7. Checkout allows no guest orders

`createOrder()` requires a session, and the RLS insert policy requires
`user_id = auth.uid()`. A visitor must create an account to buy.

Deliberate — it makes order history and loyalty points coherent — but it is a
conversion cost. Guest checkout would need a nullable-`user_id` insert path with
its own policy, and orders retrievable by reference plus phone number.

### 8. Seed image URLs are borrowed and will expire

`supabase/seed.sql` and `lib/dev-fixtures.ts` point at
`lh3.googleusercontent.com` URLs carried over from the original hardcoded
catalogue. They are not Kelmon's, not permanent, and will eventually 404.

**Fix:** upload real product photography to the `product-images` bucket and
update the seed.

### 9. `TransactionDesc` length cap is a guess

`TRANSACTION_DESC_MAX = 60` in `lib/mpesa.ts`. Safaricom's documented limit is
lower in places and inconsistently enforced. Harmless (the string is truncated),
but worth confirming against the Daraja spec for the live shortcode.

### 10. No automated tests

There is no test suite. Verification so far has been manual: typecheck, build,
route smoke tests, and the dev-auth guard checks in
[ADR-0005](../architecture/decisions/0005-dev-auth-fallback.md).

**Highest-value first tests**, in order:

1. RLS policies — a customer cannot read another's orders, cannot change their
   own `role`, cannot insert a paid order.
2. `/api/orders` re-pricing — a tampered price is ignored.
3. `normalizeKenyanPhone()` — table-driven, including rejections.
4. `award_loyalty_points()` — a second call awards zero.

The RLS tests are the ones worth writing first: they cover the actual security
boundary, and they are cheap against a local Supabase stack.

### 11. Pre-existing lint warnings

Four warnings in Kelmon components untouched by the merge: unused variables in
`CircleCollection.tsx`, `HeroSlider.tsx`, `ProductCarousel.tsx`, and a
`no-page-custom-font` warning for the Material Symbols stylesheet in
`app/layout.tsx`. Cosmetic.
